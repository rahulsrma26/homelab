# Tang server on a single-board computer

A bare-metal Tang server on an **Orange Pi Zero 3** (Armbian), as used for the two Tang servers that unlock the hosts' encrypted disks ([zfs-encryption.md](zfs-encryption.md), design in [architecture/encryption.md](../architecture/encryption.md)). Two boards are built identically from this guide; with Shamir 1-of-2 either one can unlock every host.

Why a separate board: Tang must not depend on the machines it unlocks, and must not sit next to them (someone taking a host *and* its Tang can unlock it). A board draws ~2 W and boots in well under a minute after a power cut, before any host asks.

## Hardware

| | |
|---|---|
| Board | Orange Pi Zero 3 (Allwinner H618, 4× Cortex-A53), 4 GB is plenty |
| Storage | a **high-endurance** microSD card (e.g. SanDisk High Endurance, Samsung PRO Endurance): a consumer card is the first thing to fail |
| Network | wired (`end0`, Gigabit) or Wi-Fi (`wlan0`), on the management VLAN. Wired is simpler and survives a Wi-Fi outage; Wi-Fi lets the board sit anywhere, away from the hosts |
| Power | a real USB charger, 5 V ≥ 2.5 A. |

- **The board's address comes from a DHCP reservation tied to its MAC.** On the wired port the MAC is generated by Armbian (locally administered, `02:…`), not burned in, so **after reflashing, check the MAC is unchanged** (`ip -br link`). If it changed, update the reservation, or the Tang moves to another address and the hosts can't reach it. On Wi-Fi, check the router doesn't hand the board a randomised MAC per connection.
- Read the SD card's maker, model and date without removing it: `/sys/block/mmcblk0/device/{manfid,oemid,name,date}`.

## 1. OS

1. Download Armbian **Debian 13 Minimal / IOT for the Orange Pi Zero 3** (armbian.com or Armbian Imager). **Not the Zero 3W or Zero 2W**: their images don't boot on the Zero 3 (LEDs on without a card, dark with the card in, never on the network).
2. Flash it with Armbian Imager (verification on; for Linux and macOS), or by hand. **Pick the card's device carefully: `dd` overwrites whatever it's given.**
   ```bash
   # Linux
   lsblk -o NAME,SIZE,MODEL,TRAN          # find the card, e.g. /dev/sdX or /dev/mmcblk0
   sudo umount /dev/sdX?* 2>/dev/null
   xzcat Armbian_*.img.xz | sudo dd of=/dev/sdX bs=4M status=progress conv=fsync

   # macOS
   diskutil list                          # find the card, e.g. /dev/disk4
   diskutil unmountDisk /dev/disk4
   xzcat Armbian_*.img.xz | sudo dd of=/dev/rdisk4 bs=4m status=progress
   ```
3. Card in until it clicks, power on. Red and green LEDs blink while it boots. **Don't pull the power during the first boot** (it resizes the filesystem and generates keys). Find it in the router's DHCP list.
4. SSH in as root (default password `1234`); Armbian forces a new password and asks you to create a user.
5. **On Wi-Fi:** connect it to the SSID of the management VLAN (`nmtui`, or `armbian-config` → Network). **Either way:** give it a DHCP reservation (fixed address) on the management VLAN.

## 2. SSH

Copy your key first (`ssh-copy-id <user>@<board>`) and check a key login works, then:

```bash
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart ssh
sshd -T | grep -E 'permitrootlogin|passwordauthentication'    # both "no"
```

## 3. Fewer SD card writes

**`/etc/fstab`:** `noatime` and a longer commit on root; logs and temp files in RAM:

```
UUID=<root-uuid> / ext4 defaults,noatime,commit=120,errors=remount-ro 0 1
tmpfs /tmp     tmpfs defaults,nosuid 0 0
tmpfs /var/log tmpfs defaults,noatime,nosuid,mode=0755,size=64m 0 0
tmpfs /var/tmp tmpfs defaults,noatime,nosuid,mode=1777,size=256m 0 0
```

`/var/tmp` needs **at least ~256 MB**: kernel updates build the initramfs there, and with 16 MB a kernel install fails with "No space left on device". Apply without a reboot: `mount -o remount /; mount /var/log; mount /var/tmp; systemctl daemon-reload`.

**Journal in RAM** (`/etc/systemd/journald.conf`), then `systemctl restart systemd-journald`:

```
Storage=volatile
RuntimeMaxUse=16M
```

**Unneeded services off:**

```bash
systemctl disable --now bluetooth.service rsyslog.service serial-getty@ttyS0.service
systemctl disable --now wpa_supplicant.service      # only on a wired board: Wi-Fi needs it
```

zram swap is in RAM: leave it on. Check the write rate after a day (under ~100 MB/day is fine):

```bash
awk '{printf "%.0f MB written since boot\n", $7*512/1024/1024}' /sys/block/mmcblk0/stat; uptime -p
```

## 4. Tang

```bash
apt update && apt install -y tang
systemctl enable --now tangd.socket
tang-show-keys                     # the thumbprint hosts are asked to trust when binding
curl -s http://localhost/adv | head -c 80
```

**Back up the keys right away** (from your workstation). Without them, hosts can't unlock automatically; with them, anyone can stand in for this Tang, so the archive is as sensitive as the disk keys: store it in your password manager (as an attachment) or encrypted, delete the local copy, and never put it in a repo.

```bash
ssh <user>@<board> "sudo tar czf - -C / var/lib/tang" > tang-<a|b>-keys-$(date +%F).tar.gz
# → into the password manager, then: rm tang-<a|b>-keys-*.tar.gz
```

**Taking over an existing Tang** (a new board, a rebuilt card): restore the old `/var/lib/tang/*.jwk` instead of using fresh keys.

- Check each file with `jose jwk thp -i <file>`: it must print the file's own name (the name is the key's thumbprint).
- Owner `_tang` on Debian 13 (`tang` on older), mode 440; then `systemctl restart tangd.socket`.
- **Same address as before:** the hosts need no change. **New address:** re-bind every host ([zfs-encryption.md](zfs-encryption.md), section 4), because each host's Clevis file contains the Tang's URL.

## 5. Updates

**Debian security updates install by themselves.** Armbian's own packages (kernel, board support) are not auto-installed, so the kernel can't change unattended:

```bash
apt install -y unattended-upgrades
dpkg-reconfigure -plow unattended-upgrades      # Yes
unattended-upgrade --dry-run --debug 2>&1 | tail -20
```

Leave `Automatic-Reboot` off: a board that fails to boot unattended means its Tang is down until someone notices. Unattended upgrades keep locally changed config files (the hardened `sshd_config`).

**Everything else by hand, every few months, one board at a time** (the other keeps serving):

1. `df -h /var/tmp` shows 256M.
2. Back up the Tang keys (as above).
3. `apt update && apt full-upgrade`. Asked about a config file you changed (e.g. `sshd_config`): **keep the installed version**.
4. Don't reboot unless it finished cleanly. "Errors were encountered": `dpkg --configure -a 2>&1 | tail -40` shows why.
5. Before rebooting, check the kernel is complete: `dpkg -l 'linux-image*' | grep ^ii`; `ls -lh /boot/Image /boot/uInitrd /boot/initrd.img-*`.
6. Reboot, then:
   ```bash
   uname -r
   curl -s http://localhost/adv | head -c 80                          # Tang answering
   sshd -T | grep -E 'permitrootlogin|passwordauthentication'         # both "no"
   ip -br link                                                        # the board's MAC unchanged (end0 or wlan0)
   ```

## Watching it

An uptime monitor checks `http://<board>/adv` on each board. Logs are in RAM, so they cover only the current boot; that's intended.
